## 一、评分模型概述

### 1.1 设计理念

健康评分系统采用**基于指标严重级别的评分模型**，核心思想是：

> **评分反映问题的严重程度，而非问题的数量**

通过为不同严重级别的问题赋予不同权重，确保严重问题对评分的影响更大，从而更准确地反映集群的真实健康状况。



## 二、核心评分算法

### 2.1 评分流程

健康评分计算分为**4个步骤**：

```
步骤1: 计算每个指标的得分（0-100分）
   ↓
步骤2: 按严重级别分组（一级、二级、三级）
   ↓
步骤3: 计算各级别的平均分
   ↓
步骤4: 按严重级别权重汇总得到总分
```

### 2.2 核心公式

```
总评分 = 一级平均分 × 20% + 二级平均分 × 30% + 三级平均分 × 50%
```

**关键特性**：
- 相同严重级别的指标**权重相等**（平均分配该级别的权重）
- 某级别无指标时，该级别平均分视为**100分**（满分）
- 评分范围：**0-100分**

### 2.3 计算示例

假设某集群巡检结果：

**一级告警（优化建议）**：2个指标
- 索引删除保护配置：得分 80分
- ILM配置：得分 90分
- **一级平均分** = (80 + 90) / 2 = **85分**

**二级告警（建议处理）**：5个指标
- JVM堆大小一致性：得分 70分
- 主分片数合理性：得分 75分
- 副本数量合理性：得分 80分
- 线程池使用情况：得分 65分
- 节点资源使用：得分 85分
- **二级平均分** = (70 + 75 + 80 + 65 + 85) / 5 = **75分**

**三级告警（必须处理）**：0个指标
- **三级平均分** = **100分**（无三级问题视为满分）

**总评分计算**：
```
总分 = 85 × 20% + 75 × 30% + 100 × 50%
     = 17 + 22.5 + 50
     = 89.5分
```

**健康等级**：良好（≥75分）

### 2.4 算法优势

#### 场景1：告警多但评分高
- 任务A：8个二级告警，平均分88分 → 评分可能更高
- 任务B：4个二级告警，平均分70分 → 评分可能更低

**原因**：评分看的是**质量（平均得分）**而非**数量**。如果8个告警都是轻微问题（得分高），平均分依然很高。

#### 场景2：少量严重问题导致评分骤降
- 1个三级问题（得分0分）占50%权重
- 即使其他指标都是满分，总分也会被拉低到50分左右

**原因**：三级问题的高权重确保严重问题不会被掩盖。

## 四、指标得分计算

### 4.1 指标类型

系统支持3种指标类型，采用不同的评分算法：

#### 4.1.1 数值型指标（numeric）

**特点**：有明确的数值和阈值，采用**线性插值算法**

**配置示例**：
```yaml
disk_usage_percent:
  type: numeric
  direction: lower  # 越小越好
  thresholds:
    normal: 70      # 正常阈值
    warning: 85     # 警告阈值
    critical: 95    # 严重阈值
```

**评分规则**（direction: lower，越小越好）：
- 值 ≤ normal（70）：**100分**（优秀）
- normal < 值 ≤ warning（70-85）：**60-99分**（线性插值）
  - 公式：`60 + 40 × (warning - value) / (warning - normal)`
- warning < 值 ≤ critical（85-95）：**0-59分**（线性插值）
  - 公式：`60 × (critical - value) / (critical - warning)`
- 值 > critical（95）：**0分**（严重）

**评分规则**（direction: higher，越大越好）：
- 值 ≥ normal：**100分**
- warning ≤ 值 < normal：**60-99分**
- critical ≤ 值 < warning：**0-59分**
- 值 < critical：**0分**

**示例**：
```
磁盘使用率 75%（normal=70, warning=85, critical=95, direction=lower）
得分 = 60 + 40 × (85 - 75) / (85 - 70)
     = 60 + 40 × 10/15
     = 60 + 26.67
     = 86.67分
```

#### 4.1.2 枚举型指标（enum）

**特点**：离散的状态值，直接映射到分数

**配置示例**：
```yaml
status:
  type: enum
  direction: higher
  values:
    GREEN: 100    # 绿色状态
    YELLOW: 60    # 黄色状态
    RED: 0        # 红色状态
```

**评分规则**：
- GREEN → 100分
- YELLOW → 60分
- RED → 0分

#### 4.1.3 布尔型指标（boolean）

**特点**：通过/未通过的二元判断

**配置示例**：
```yaml
destructive_requires_name:
  type: boolean
  severity: warning  # 未通过时的严重程度
```

**评分规则**：
- passed = true（通过）：**100分**
- passed = false（未通过）：
  - severity = critical → **0分**
  - severity = warning → **60分**

### 4.2 降级处理

当指标配置与实际数据类型不匹配时，系统会自动降级：

- **数值型配置 + 字典类型值** → 降级为布尔型评分
- **枚举型配置 + 字典类型值** → 降级为布尔型评分

降级规则：
- passed = true → 100分
- passed = false → 60分（warning）或 0分（critical）

## 五、健康等级判定

### 5.1 等级划分

| 评分范围 | 健康等级 | 颜色标识 | 说明 |
|---------|---------|---------|------|
| 90-100分 | **优秀** | 🟢 绿色 | 集群运行状态良好，无明显问题 |
| 75-89分 | **良好** |  蓝色 | 集群运行状态正常，存在少量轻微问题 |
| 60-74分 | **一般** | 🟡 黄色 | 集群运行状态基本正常，但存在一些需要关注的问题 |
| 40-59分 | **警告** | 🟠 橙色 | 集群存在较多问题，需要及时处理 |
| 0-39分 | **严重** | 🔴 红色 | 集群存在严重问题，需要立即处理 |

### 5.2 判定代码

```python
def _get_health_level(score: float) -> str:
    if score >= 90:
        return '优秀'
    elif score >= 75:
        return '良好'
    elif score >= 60:
        return '一般'
    elif score >= 40:
        return '警告'
    else:
        return '严重'
```

## 六、配置文件说明

### 6.1 配置文件清单

系统使用2个核心配置文件：

| 配置文件 | 路径 | 用途 |
|---------|------|------|
| severity_level_weights.yaml | `configs/` | 定义严重级别权重 |
| indicator_weights.yaml | `configs/` | 定义指标类型、阈值、方向 |

### 6.2 severity_level_weights.yaml

**作用**：定义各严重级别的权重

**完整配置**：
```yaml
# 严重级别权重配置
# 定义各严重级别的权重（总和应为1.0）

severity_levels:
  level_1:
    weight: 0.20
    description: "一级告警 - 优化建议（不严重）"
  
  level_2:
    weight: 0.30
    description: "二级告警 - 建议处理（一般）"
  
  level_3:
    weight: 0.50
    description: "三级告警 - 必须处理（非常严重）"

# 说明：
# 1. 可根据实际业务需求调整权重，但需确保总和为1.0
# 2. 相同严重级别的指标自动平均分配该级别的权重
# 3. 如果某级别没有指标，则该级别不参与评分计算
```

**修改建议**：
- ✅ 可根据业务场景调整权重（如更关注三级问题可调高level_3权重）
- ⚠️ **必须确保三个权重之和为1.0**
- ⚠️ 修改后需重启服务或重新巡检才能生效

### 6.3 indicator_weights.yaml

**作用**：定义每个指标的类型、阈值、方向等评分参数

**配置结构**：
```yaml
indicators:
  # 维度/类别名称
  cluster_health:
    # 指标名称
    status:
      weight: 0.30              # 指标权重（历史遗留字段，当前算法不使用）
      type: enum                # 指标类型：enum/numeric/boolean
      direction: higher         # 方向：higher（越大越好）/lower（越小越好）
      values:                   # 枚举值映射（仅enum类型）
        GREEN: 100
        YELLOW: 60
        RED: 0
    
    active_shards_percent:
      weight: 0.15
      type: numeric
      direction: higher
      thresholds:               # 阈值配置（仅numeric类型）
        normal: 95              # 正常阈值
        warning: 90             # 警告阈值
        critical: 80            # 严重阈值
  
  cluster_destructive:
    destructive_requires_name:
      weight: 0.05
      type: boolean
      severity: warning         # 未通过时的严重程度：warning/critical
```

**配置参数说明**：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| type | string | ✅ | 指标类型：`enum`/`numeric`/`boolean` |
| direction | string | ⚠️ | 仅numeric类型：`higher`（越大越好）或`lower`（越小越好） |
| values | dict | ⚠️ | 仅enum类型：枚举值到分数的映射 |
| thresholds | dict | ⚠️ | 仅numeric类型：包含normal/warning/critical三个阈值 |
| severity | string | ️ | 仅boolean类型：未通过时的严重程度`warning`或`critical` |

**修改建议**：
- ✅ 调整阈值以匹配实际业务需求（如调整磁盘使用率的normal/warning/critical值）
- ✅ 修改direction以符合指标特性（如使用率类指标用lower，活跃度用higher）
- ⚠️ 新增指标时需同时更新 `_get_severity_level()` 方法中的级别映射
- ⚠️ 修改后需重新巡检才能生效

### 6.4 严重级别映射（代码配置）

**位置**：`es_insight/parse_check_result.py` 中的 `_get_severity_level()` 方法

**配置方式**：
```python
severity_map = {
    # 精确匹配
    ('cluster_health', 'status'): 3,
    ('cluster_destructive', 'destructive_requires_name'): 1,
    
    # 通配符匹配（整个类别）
    ('jvm_consistency', '*'): 2,
    ('cluster_settings', '*'): 1,
    
    # ... 更多映射
}
```

**匹配规则**：
1. 优先精确匹配 `(category, check_name)`
2. 其次通配符匹配 `(category, '*')`
3. 均未匹配则返回默认级别 **2**

**修改建议**：
- ✅ 根据 `指标严重级别.md` 文档调整映射关系
- ✅ 新增检查项时需添加对应的级别映射
- ⚠️ 修改后需重启服务或重新巡检才能生效

## 七、使用指南

### 7.1 调整评分权重

#### 场景1：更关注严重问题

**目标**：提高三级问题的影响力

**操作**：
```yaml
# configs/severity_level_weights.yaml
severity_levels:
  level_1:
    weight: 0.15  # 降低一级权重
  level_2:
    weight: 0.25  # 降低二级权重
  level_3:
    weight: 0.60  # 提高三级权重
```

**效果**：三级问题对总分的影响从50%提升到60%

#### 场景2：均衡各级别影响

**目标**：三个级别平等对待

**操作**：
```yaml
severity_levels:
  level_1:
    weight: 0.33
  level_2:
    weight: 0.33
  level_3:
    weight: 0.34
```

### 7.2 调整指标阈值

#### 场景1：集群规模较大，放宽阈值

**目标**：避免因规模大导致评分偏低

**操作**：
```yaml
# configs/indicator_weights.yaml
node_performance:
  shards_per_node:
    type: numeric
    direction: lower
    thresholds:
      normal: 500     # 原300 → 500
      warning: 800    # 原500 → 800
      critical: 1200  # 原800 → 1200
```

#### 场景2：业务要求更高，收紧阈值

**目标**：提高标准，及早发现问题

**操作**：
```yaml
cluster_health:
  active_shards_percent:
    type: numeric
    direction: higher
    thresholds:
      normal: 99      # 原95 → 99
      warning: 97     # 原90 → 97
      critical: 95    # 原80 → 95
```

### 7.3 新增检查项

**步骤**：

1. **在 `indicator_weights.yaml` 中添加指标配置**：
```yaml
new_category:
  new_check:
    type: numeric
    direction: lower
    thresholds:
      normal: 10
      warning: 20
      critical: 30
```

2. **在 `_get_severity_level()` 方法中添加级别映射**：
```python
severity_map = {
    # ... 现有映射
    ('new_category', '*'): 2,  # 添加新类别的级别
}
```

3. **在 `_generate_check_results()` 方法中生成检查数据**：
```python
check_results['new_category'] = {
    'new_check': {
        'value': actual_value,
        'passed': actual_value < 10,
        'message': f"新检查项：{actual_value}"
    }
}
```

4. **重新运行巡检任务**

### 7.4 排查评分异常

#### 问题1：评分与预期不符

**排查步骤**：

1. **查看详细评分报告**（HTML/Word报告中的"健康评分详情"）
2. **检查各级别平均分**：
   - 一级平均分
   - 二级平均分
   - 三级平均分
3. **对比指标详情**：
   - 哪些指标得分低？
   - 这些指标属于哪个严重级别？
4. **检查阈值配置**：
   - 阈值是否合理？
   - direction是否正确？

#### 问题2：某指标得分异常

**排查步骤**：

1. **检查指标配置**：
   ```python
   # 查看 indicator_weights.yaml 中的配置
   config = self._get_indicator_config(dimension, category, check_name, indicator_weights)
   ```

2. **检查实际值类型**：
   - 是否为预期的数值/字符串/布尔值？
   - 是否触发了降级处理？

3. **查看日志**：
   ```
   计算指标 xxx 得分失败: {error_message}
   字典类型value降级为布尔评分
   ```

#### 问题3：级别映射不正确

**排查步骤**：

1. **检查映射表**：
   ```python
   # 在 _get_severity_level() 方法中
   severity_map = {...}
   ```

2. **检查匹配规则**：
   - 是否精确匹配？
   - 是否通配符匹配？
   - 是否使用了默认级别2？

3. **查看调试日志**：
   ```
   未找到 {category}.{check_name} 的级别配置，使用默认级别 2
   ```

## 八、常见问题（FAQ）

### Q1: 为什么告警多的任务评分反而更高？

**A**: 因为评分看的是**各级别的平均得分**，而非告警数量。

**示例**：
- 任务A：8个二级告警，平均分88分 → 二级贡献 = 88 × 30% = 26.4分
- 任务B：4个二级告警，平均分70分 → 二级贡献 = 70 × 30% = 21分

如果其他级别相同，任务A的总分会更高。这说明任务A的8个问题都是**轻微问题**（得分高），而任务B的4个问题更严重（得分低）。

### Q2: 如何理解"相同严重级别的指标权重相等"？

**A**: 在同一个严重级别内，所有指标的权重完全相同，通过平均分体现。

**示例**：
- 二级有10个指标，每个指标的实际权重 = 30% / 10 = 3%
- 二级有5个指标，每个指标的实际权重 = 30% / 5 = 6%

指标越多，单个指标的影响力越小；指标越少，单个指标的影响力越大。

### Q3: 为什么没有三级问题时，三级平均分是100分？

**A**: 这是算法的**边界处理**机制。

**原因**：
- 如果没有该级别的指标，说明该级别没有问题
- 视为满分（100分）是合理的，因为"没有问题就是最好的状态"
- 这也避免了除零错误

### Q4: 如何快速提升评分？

**A**: 优先解决**三级问题**，因为：
- 三级问题占50%权重，影响最大
- 解决1个三级问题（0分→100分）比解决10个一级问题提升更明显

**优先级建议**：
1. 🚨 首先解决所有三级问题（必须处理）
2. ⚠️ 其次优化二级问题（建议处理）
3. 💡 最后考虑一级问题（优化建议）

### Q5: 评分会受指标数量影响吗？

**A**: 间接影响，但不是直接关系。

**说明**：
- 某级别指标越多，单个指标的平均分权重越小
- 但如果新增的指标得分都很高，会拉高该级别平均分
- 如果新增的指标得分都很低，会拉低该级别平均分

**关键**：评分取决于**平均质量**，而非**绝对数量**。

### Q7: 修改配置后需要重启服务吗？

**A**: 取决于修改的内容：

| 修改内容 | 是否需要重启 | 说明 |
|---------|------------|------|
| severity_level_weights.yaml | ✅ 需要 | 权重配置在初始化时加载 |
| indicator_weights.yaml | ✅ 需要 | 指标配置在初始化时加载 |
| _get_severity_level() 代码 | ✅ 需要 | 代码修改需重启服务 |
| 阈值调整 | ❌ 不需要 | 下次巡检时自动生效 |

### Q8: 历史任务的评分会受影响吗？

**A**: 不会。

**说明**：
- 历史任务的评分数据已存储在数据库中
- 新的评分算法只影响新任务
- 历史数据保持不变

### Q9: 如何验证评分算法是否正确？

**A**: 通过以下步骤验证：

1. **手动计算**：
   - 提取各级别指标得分
   - 计算各级别平均分
   - 按公式计算总分

2. **对比系统输出**：
   - 查看HTML/Word报告中的评分详情
   - 对比手动计算结果与系统输出

3. **使用测试脚本**（如需要）：
   - 创建模拟数据
   - 运行评分算法
   - 验证结果

### Q10: 评分系统支持自定义严重级别吗？

**A**: 当前版本支持3个级别，暂不支持自定义级别数量。

**未来规划**：
- 可扩展支持更多级别（如4级、5级）
- 需要修改评分算法和配置文件结构
- 需要更新前端展示逻辑

## 十、最佳实践

### 10.1 配置管理

1. **版本控制**：
   - 将配置文件纳入Git版本控制
   - 每次修改配置文件时提交commit并说明原因

2. **环境区分**：
   - 开发/测试/生产环境使用不同的阈值配置
   - 生产环境阈值更严格，测试环境可适当放宽

3. **文档同步**：
   - 修改配置时同步更新本文档
   - 记录修改原因和影响范围

### 10.2 阈值调优

1. **基于历史数据**：
   - 收集至少1个月的巡检数据
   - 分析各项指标的分布情况
   - 根据P95/P99分位数设置阈值

2. **渐进式调整**：
   - 不要一次性调整过多阈值
   - 每次调整1-2个指标，观察效果
   - 记录调整前后的评分变化

3. **业务场景适配**：
   - 核心业务集群：阈值更严格
   - 测试/开发集群：阈值可适当放宽
   - 不同业务类型（搜索/日志/分析）使用不同阈值

### 10.3 问题处理

1. **优先级排序**：
   ```
   P0: 三级告警（必须处理）→ 24小时内解决
   P1: 二级告警（建议处理）→ 1周内解决
   P2: 一级告警（优化建议）→ 1个月内优化
   ```

2. **根因分析**：
   - 不要只看评分，要查看具体的指标详情
   - 分析指标异常的根本原因
   - 制定针对性的优化方案

3. **效果验证**：
   - 优化后重新运行巡检
   - 对比优化前后的评分变化
   - 确认问题是否真正解决

### 10.4 监控告警

1. **评分趋势监控**：
   - 跟踪评分的周/月趋势
   - 设置评分下降的告警阈值（如单周下降>10分）

2. **关键指标监控**：
   - 重点关注三级指标的得分
   - 对持续低分的指标设置专项监控

3. **自动化报告**：
   - 定期生成巡检报告
   - 自动发送给相关负责人
   - 建立问题跟踪机制
